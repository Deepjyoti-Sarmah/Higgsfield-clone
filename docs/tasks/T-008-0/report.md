## Open issues / guesses / things skipped
- **`TOPUP`, not `GRANT`.** The instruction said the endpoint "writes a GRANT ledger row". A `GRANT` is impossible without a migration: `uq_ledger_entry_guest_grant` is a **partial unique index on `(user_id) WHERE kind = 'GRANT'`** and every guest already got one at account creation, so a second `GRANT` raises a unique violation. The ledger already pre-provisions `TOPUP` (DB check constraint, `LedgerKind`, amount-sign rule, `job_id IS NULL` requirement) with exactly the intended semantics and unused until now. Design § **Why `TOPUP`, not `GRANT`** documents it; no existing route/schema changed.
- **Scope conflict resolved by D-013.** D-012's P1 list says "pricing with a fake top-up" while `PLAN.md` § Scope and D-007 put it in the P0 loop. Per the direct instruction (P0-simple) and `PLAN.md`, spec 008 is **P0**; D-013 records the resolution (DECISIONS is append-only, so D-012 was not edited).
- **A draft inaccuracy caught and fixed:** the design first said "no 422". `require_current_user` declares an optional `session` cookie parameter, so FastAPI adds a 422 — identical to the existing `GET /credits`. Corrected in `design.md` and in the T-008-1 brief.
- **Two deliberate P0 cuts**, both documented in the spec's Open questions: no credit-history list (would need a second route `GET /credits/entries`) and no top-up cap (P1; `POST /auth/guest` is already an unbounded faucet, and D-003's `PAID_BUDGET_CENTS` + the `GENERATION_BACKEND=mock` kill switch are the real guards).
- **Client/server constant duplication.** The button label needs `100` before any response exists, so `TOP_UP_CREDITS = 100` lives on the client too; the *confirmation* renders the API's `amount`/`balance`, so a drift can never lie to the user. Returning the bundle size from `GET /credits` would be a schema change (out of scope).
- **`.agent-logs/` for a DSH session is hand-exported.** There is no automatic DSH exporter in the repo (the Claude Code hooks in `.claude/hooks/capture.py` do not cover this harness), so this session's log was written by hand in the same format the committed T-005-0/T-007-0 logs use.
- **The route is a 501 stub until T-008-1**, so a full `verify-slice` must run after T-008-1; the stub keeps the contract stable meanwhile, which is the point of freezing it first.
