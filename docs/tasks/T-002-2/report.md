## Deviations from the brief (flagged, not silent)
- **TypeScript version:** `npm create vite@latest` scaffolded `typescript@~6.0.2` (installed `6.0.3`), but `openapi-typescript@7.13.0`'s peer range is `^5.x`. A plain `npm install` (as the verify command uses, no flags) throws `ERESOLVE` against that peer conflict. Pinned `typescript` to `^5.9.3` instead — well within strict-mode support and satisfies the peer range, so `npm install` alone works cleanly (confirmed with a from-scratch `rm -rf node_modules package-lock.json && npm install`).
- **`eslint-plugin-react-hooks` v7 "recommended" preset:** its `recommended-latest`/`flat.recommended` configs are aimed at the React Compiler and use a legacy (non-flat) `plugins: ["react-hooks"]` array on some sub-configs (breaks ESLint 10 flat config), and the parts that are flat-compatible add rules like `set-state-in-effect` that flag the standard "fetch in `useEffect`, `setState` in the callback" pattern used by `useSession`. Registered the plugin manually and enabled only `rules-of-hooks` (error) and `exhaustive-deps` (warn) — the two rules STANDARDS/the brief actually ask for ("react-hooks rules"), without the compiler-oriented additions.
- **`@typescript-eslint/naming-convention`:** a `variable` selector scoped to `types: ['function']` (to force only components, i.e. function-valued variables, into PascalCase) requires type-aware linting (`parserOptions.project`), which errors without a configured TS program. Used a type-unaware rule instead: `function` and `variable` selectors both allow `camelCase` **or** `PascalCase` (components are exported as `function ComponentName()`, i.e. the `function` selector, so PascalCase must be allowed there; plain helper functions stay camelCase by convention, not by a rule ESLint can check without type info).
